# Attached review: implementation and verification

This report records the changes made from the attached senior-engineering review and what the evidence does—and does not—show. The starting point in that review was commit `dc0e133`; these changes are currently local and uncommitted.

## Karthik repository review

Following the user's direction, I inspected [JatothKarthikKumar/signalpost-company-research-agent](https://github.com/JatothKarthikKumar/signalpost-company-research-agent), the public repository link identified earlier. The repository contains a small Python package with `agent.py`, `entity_resolver.py`, `storage.py`, `sources_client.py`, `synthesizer.py`, and typed Pydantic schemas. Its agent uses an `asyncio.Semaphore` and `asyncio.gather` for bounded concurrent requests; its pipeline separates BRREG, source clients, storage and synthesis; its resolver validates Norwegian organisation-number checksums; and its SQLite store records profile facts and changes.

**Techniques worth keeping and how this project handles them:**

- Bounded concurrency: the existing runner already uses a bounded worker pool; the new global request cap and batch deadline now apply around that work. I kept the current synchronous/thread-pool architecture because swapping the network stack to `httpx`/asyncio would be a broad rewrite without a measured performance need.
- Clear source boundaries: the project already has separate BRREG, NAV, Wikidata, TinyFish, Tavily, Brave and LLM modules; this change strengthens their shared request-budget hooks and independent failure behavior.
- Typed output contract: the project uses explicit claim families/statuses and regression checks rather than introducing an unpinned Pydantic dependency. A clean-room clone still needs to verify this contract at the exact commit.
- Change history: the source-specific snapshot key in this project is stricter than a single current fact per field because it prevents two URLs in the same family from appearing to overwrite one another.

I did not import Karthik's code. His public repository's README is only a short project description, and the visible implementation focuses on BRREG identity, roles, accounts and NAV jobs; it does not demonstrate the website-discovery, legal-page identity, deep job/news extraction, gold-set evaluation, or verified score methodology needed to transplant those parts. This is an architecture comparison, not proof that any technique caused the leaderboard score. The score page is a directional score for a 300-company evidence set, not a complete diagnostic of source behavior.

## Implemented in this revision

| Review finding | Change | Regression coverage |
| --- | --- | --- |
| History for several sources in one family could overwrite itself | SQLite history now keys each source by organisation, family, and canonical source URL. Snapshots keep the extracted payload and source URL. Existing tables migrate into a legacy source without discarding their rows. | Same source unchanged, two sources independent, old database migration. |
| `finish()` could replace a successful LLM summary | Enrichment and evidence finalization run before optional summary generation; finalization preserves an accepted LLM summary. | Summary survives finalizer; main pipeline ordering. |
| Search providers stopped on unverified registry/Wikidata state | Recovery discovery is gated on a *verified, published website claim*. Outages and unverified candidates from one provider do not prevent an independent provider from trying. | Registered-but-unverified URL, Wikidata failure and successful-provider fallback. |
| Domain/name similarity could reject trading brands | Similarity ranks candidate URLs but does not establish identity or discard the lead. Search results remain leads. | Domain-mismatched candidate retained; publication still requires entity verification. |
| Exact-number directory and marketplace profiles were mislabeled as company-owned websites | Added shared directory, marketplace and social-host rejection before fetch/publication, including hosts found in the live sample. A directory entry may corroborate which company the page describes, but is never a company homepage, careers source, or public-activity source. Other search candidates now need a same-host legal/contact/about page to tie them to the legal entity. A number embedded in a product code is ignored unless explicitly labelled as an organisation number. | Firmalisten website rejection without a network request; TinyFish rejects directory/marketplace candidates; number-in-product-code rejection; candidate without legal-page corroboration is held ambiguous. |
| Homepage-only identity check could miss legal evidence | For a candidate site, the collector can inspect up to three same-host about/contact/legal/privacy/company pages, subject to robots, URL safety, size, and request limits. The verified claim cites both homepage and identity page. | Legal page containing exact organisation number; limits and evidence IDs. |
| Brand mentions could be mistaken for the legal entity | Exact organisation number or the full registered legal name is required. A suffix-stripped name, one-word brand, repeated mention, or domain resemblance is not identity proof. Parent/subsidiary relationships are not inferred from a shared domain. | Brand-only and suffix-only false matches rejected; exact number and full legal name accepted. |
| Useful vacancies/articles were behind listing pages; JSON-LD was unused | The bounded collector parses JSON-LD and may follow one eligible same-host detail link from a careers/news listing. JobPosting and article evidence must attribute to the exact organisation; vacancies must also pass date/activity checks. | Exact-vs-mismatched hiring organisation, dated publisher attribution, bounded detail traversal. |
| Registered `http://` sites were abandoned | A registered HTTP URL is upgraded to HTTPS before the ordinary safety, robots, redirect, and identity checks. | HTTP-to-HTTPS behavior and redirect safeguards. |
| NAV employer-name filtering could miss a trading-name posting | Fuzzy token overlap now queues a candidate detail fetch, but publication still requires exact organisation-number or the existing corroborated legal-name/location checks. Funnel counts expose seen, queued, fetched, mismatch, and expiry stages. | Trading-name candidate accepted only when its detail has the exact organisation number. |
| Late batch work could exceed runtime and lose all output | Added a batch collection deadline, finalization reserve, per-company checkpoint, `--resume`, and terminal envelopes for companies not reached before cutoff. Optional stages defer when the work cutoff is reached. | CLI checkpoint/resume and complete output envelope behavior. |
| Separate provider caps could exceed the shared daily request ceiling | A thread-safe run-wide request counter now covers HTTP fetches/retries and the search, NAV, Wikidata, and model connectors. CLI refuses a configured ceiling above 2,000. | Shared counter limit and provider hook tests. |
| LLM rate-limit failures were opaque and repeated | Summary reports preserve HTTP status and `Retry-After`; HTTP 429 opens a run-wide circuit so later company summaries do not repeat doomed calls. | Mocked 429 diagnostics and circuit breaker. |
| Summary checks allowed unsupported non-numeric sentences and loose references | The LLM output is mapped sentence-by-sentence to specific fact-field references; each sentence must overlap its selected facts, and numeric tokens are checked against those selected fields. Summary input is a bounded catalogue of already verified claims, with reporting-period and promotional-source metadata. | Field-specific sentence refs and unsupported nonnumeric statement rejection. |
| Candidate-only “judge” added requests but not scored facts | The CLI explicitly excludes/rejects the web-search judge from the competition pipeline. Its candidates are not promoted to verified claims. | Reported `excluded_from_competition_pipeline`; CLI option validation. |

The user's identity rule is preserved: a legal suffix can help normalize or rank a name, but matching a suffix—or a suffix-free brand—does not establish that two records are the same entity. Only exact organisation-number evidence or the configured full-name/corroboration checks can clear the publication gate.

## Not claimed complete

1. **Independent gold-set benchmark:** the audit's proposed manually checked set is not replaced by synthetic fixtures. A human-verified dataset covering trading names, old domains, group sites, real/false vacancies, news, low-information companies, unchanged refreshes, and provider outages still needs to be assembled and run. No new recall/precision score is reported.
3. **Fresh live 100/1,000 run and official score:** the corrected live sample has only 10 companies and is capped at 250 requests. It does not replace the 100-company smoke test, 1,000-profile requirement, or Builderr's official score. No score improvement is claimed without a new controlled run and the evaluator's checked set.
4. **Cost ceiling:** the code enforces the 2,000-request ceiling and reports provider usage/cost estimates. It cannot guarantee the challenge's dollar ceiling for every account/provider configuration because provider billing and credit plans vary and are not all exposed as a preflight dollar amount. Keep paid providers off unless the expected cost is known; the default run makes no LLM or search API calls.
5. **Per-company external cursor persistence:** checkpoints store completed company profiles, but a provider's internal pagination cursor is not separately persisted. A resumed optional stage can revisit some provider work for unfinished companies; request count remains subject to the same run ceiling.
6. **Fresh dashboard rendering / Pages deployment:** source CSS and the checked-in frozen dashboard were not freshly exercised in desktop/mobile browsers as part of this change. GitHub Pages state also was not changed or asserted here.
7. **One-command clean-room run and submission freeze:** these changes have not yet been tested from a fresh clone at the new commit. This artifact is not an official Builderr submission, and no submission email was sent.

## Recommended next validation

Run the exact current code against a fixed, independently audited development set, preserve the before/after input and output files, manually adjudicate every newly published website/job/activity item, then compare coverage, fact precision/recall, entity errors, request count, wall time, provider usage, and unchanged-run false changes. Only after that should the exact commit and run command be frozen for Builderr's clean-room evaluator.
